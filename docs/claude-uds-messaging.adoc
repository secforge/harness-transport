= Claude Code session-to-session messaging (`uds-messaging`)
:toc:
:toclevels: 3
:description: The undocumented unix-socket protocol Claude Code sessions use to message each other on one machine — socket layout, token authentication, wire format, message types, and how to write a third-party client.
:keywords: claude, claude-code, uds, unix socket, ipc, protocol, interoperability, messaging, peer

Claude Code sessions on the same machine talk to each other over Unix domain
sockets. This document calls the observed transport `uds-messaging` (`UDS`
means Unix domain socket). Claude's official
https://code.claude.com/docs/en/cross-session-messaging[Cross-session messaging]
documentation uses `uds:` for local session addresses. The transport backs
cross-session messaging and idle notifications.

This page documents the observed wire behavior of **Claude Code 2.1.272**
(`linux-x64`), not a published protocol specification. See
<<_provenance_and_caveats>> before relying on it.

TIP: The shortest possible client is one line of shell — see
<<_writing_a_client>>. Everything else here is detail you only need when that
line is not enough.

[NOTE]
====
[.red]#[code]# marks a claim that **cannot** be established by watching two
Claude Code sessions talk to each other, or by inspecting what they leave on
disk. Those come from reading the JavaScript inside the shipped binary. They are
the claims to re-verify after an upgrade: nothing on the wire announces when one
of them stops being true, and several describe branches a normal exchange never
takes.
====

== Overview

[cols="1,4"]
|===
| Aspect | Value

| Transport | unix domain socket (Windows: named pipe), one per session
| Framing | newline-delimited JSON, one object per line
| Authentication | 128-bit token
| Identity | the connecting process's pid, taken from the socket — not from what the sender claims
| Message types | `user`, `control` (probably more)
| Direction | bidirectional; replies go to the sender's own socket
|===

== Transport and discovery

=== Socket location

Sockets live in `/run/user/<uid>/cc-socks/`, which must be mode `0700` and owned
by the caller or root. Claude Code binds `<pid>.sock` there. Not all socket file names are accepted — we bind `<pid>-<8hex>.sock`, which is
both accepted and free of pid collisions across pid namespaces.

Claude Code exports its socket path as `CLAUDE_CODE_MESSAGING_SOCKET` to child
processes after the inbox is bound, allowing them to identify their parent
session.

== Authentication

A session has two tokens, each 32 hex chars, and either one authenticates:

[cols="1,4"]
|===
| Token | Where to get it

| `CLAUDE_CODE_MESSAGING_TOKEN`
| from the environment — inherited by anything the
  session spawns.

| `peerToken`
| The key file under `~/.claude/sessions/` (mode `0700` dir, `0600` file), so
  readable by the same uid.
|===

=== The key file

[source]
----
~/.claude/sessions/<pid>.<sha256(canonical socket path)>.key
----

The 64-hex component is `sha256` of the **canonical socket path** (on Windows,
of `\\.\pipe\<name>`), which binds a key file to one specific socket — verified by
recomputing the hash against every sampled file.

Content:

[source,json]
----
{
  "peerToken": "2f6c…",                     // 32 hex chars
  "procStart": "1162506",                   // /proc/<pid>/stat field 22
  "pidDomain": "linux:<machine-id>:<target of /proc/self/ns/pid>"   // namespace-qualified pid space
}
----

=== The auth line

Whether a receiver requires authentication is described in
<<_when_authentication_is_required,When authentication is required>>. When it
does, the first line of a connection must be an auth frame; when it does not,
the first line may be an auth frame.

[source,json]
----
{"type":"auth","token":"<32 hex chars>"}
----

A line
counts as an auth frame if it is an object whose `type` is `auth`, so extra
fields are tolerated. A connection whose token matches
`CLAUDE_CODE_MESSAGING_TOKEN` is accepted as a child-process connection; a
connection whose token matches the `peerToken` from the key file is accepted
as a same-user peer connection. Both are accepted; anything else leaves the
connection unauthenticated.

[cols="2,4"]
|===
| Situation | Behaviour

| Valid token
| Connection authenticated; subsequent lines are processed.

| Auth is required and authentication is absent or invalid
| Every line is dropped and the connection destroyed. The receiver logs a
  warning to itself — _"Dropped … from a connection that did not authenticate;
  closing it"_ — and sends nothing back, so the client sees only an abrupt
  close with no reason.
  Not seen here — auth is optional on Linux and there is no setting to turn it
  on — but it is the default on Windows, so a Windows host reaches this on any
  unauthenticated connection.

| Auth is not required and no auth frame is sent
| Subsequent lines are **accepted** as unauthenticated. This is the state when
  the key file could not be published: _"peers will send unauthenticated
  (accepted: auth is optional on this platform)"_.

| Auth is not required and the auth token is wrong
| The invalid auth frame itself is dropped, but the connection remains open;
  subsequent lines are accepted as unauthenticated.
|===

[[when_authentication_is_required]]
=== When authentication is required

Claude Code's receiver may require authentication depending on the platform
and configuration. In the observed Linux configuration, authentication is
optional by default. A third-party inbox may require authentication and
publish a key file so Claude Code can obtain the accepted token. Native
Windows uses authentication by default.

IMPORTANT: In the default configuration the token is not a security boundary —
the `0700` directory is. Any process running as the same uid can both read the
key files and connect to the sockets. Treat session sockets as trusted-uid
surface, not as an authenticated channel.

=== Peer credentials

The intent is that **who you are is not something you get to state**. A sender
puts an address in `from`, but that is a claim about where replies should go,
not evidence of identity. The receiver takes identity from the kernel instead —
the credentials attached to the connection itself
(``SO_PEERCRED``footnote:peercred[A socket option on unix domain sockets:
reading it returns the pid, uid and gid of the process on the other end, as
recorded by the kernel when the connection was made. The values come from the
kernel rather than from anything sent over the socket, so a peer cannot choose
or alter them. Linux-specific; other systems have equivalents under different
names, and on Windows the named-pipe transport uses a different mechanism
entirely.]), which no sender can forge — and treats the claimed address as something to be
corroborated against it, using the session registry as the record of which
socket belongs to which process. A start time is carried alongside the pid so
that a pid which has since been recycled cannot inherit the identity of the
process that held it.

The externally visible consequence is that the `from` field does not determine
the connecting process's kernel identity. A mismatched or unverifiable address
may still allow basic delivery, but responses that depend on validating the
return address can omit fields such as `detail` on an idle notice. The exact
validation rules are described below and were established by controlled
black-box tests.

A frame carrying a `session_id` different from the receiver's is dropped;
omitting `session_id` does not trigger this check.

== Wire format

* Each frame is a newline-terminated JSON object. A final complete JSON object
  may still be processed when the connection closes without a trailing newline.
* In Claude Code 2.1.272, a connection that sends no complete line within
  **30 seconds** is disconnected.
* In the same version, a line exceeding **1 MiB** (1,048,576 bytes) closes the
  connection.
== Message types

Only two frame types were observed in the monitored sessions: `user` and
`control`. This does not establish which additional types a receiver might
accept.

=== `user`

Injects a prompt into the receiving session's queue.

[source,json]
----
{"type":"user","message":{"role":"user","content":"hello"}}
----

[cols="2,4"]
|===
| Field | Meaning

| `message.content` | The prompt text. Missing or non-string content is ignored.
| `msg_id` | Sender-assigned id, **must be an RFC-4122 UUID** — checked in two places. [.red]#[code]# On a `user` frame a non-UUID is *silently omitted* from the origin record, so every later `peer_message_status` arrives without `orig_msg_id` and correlation fails; on `notify_when_idle` a non-UUID makes the whole frame invalid and the subscription is dropped. 32 hex is **not** accepted (that pattern is the Windows pipe name).
| `msgV` | Envelope version; a session sends `1` (observed). That the receive path never reads it — and so that any value is accepted — is [.red]#[code]#.
| `priority` | Queue placement: `"now"`, `"next"` or `"later"`; absent or unknown silently becomes `"next"`, never a drop. A session sends `"next"` (observed); the rest of this row is [.red]#[code]#. `"now"` also changes *how* the frame is handled, not just where it queues: a `user` frame with `"now"` and no attachments is dispatched immediately instead of being appended to the processing chain, the same bypass control frames get (except `notify_when_idle`). So a `"now"` frame can be processed concurrently with one already in flight.
| `uuid` | [.red]#[code]# Optional string; becomes the injected prompt's uuid. Unvalidated, generated when absent — not a correlation handle.
| `from` | Reply address, `uds:<socket path>` (see <<_addressing>>). This is the address the receiver trusts, independent of the one inside the attribution envelope.
| `from_mode` | Sender's permission posture, `"bypass"` or `"prompting"` [.red]#[code]#. **Not** what the hold decision reads — see below; the gate uses the envelope's `from-mode` attribute instead.
| `file_attachments` | [.red]#[code]# Array of `{file_uuid, file_name, is_image?, sha256?, file_size?}`. Materialised locally before injection; a prefix naming the received files is prepended to the prompt.
|===

`from_mode` on the frame is *not* the value the hold decision reads, and the
distinction cost several sessions an hour. [.red]#[code]# The receiver builds
its attribution data by parsing the **attribution envelope inside
`message.content`**, and gates on the `from-mode` attribute it finds there;
the frame-level field belongs to a different lane, described as the posture
declared by a host injecting a message on local stdin. A client that sets the
frame field and not the envelope attribute asserts nothing the gate will see.

Two things follow, and the second is the trap. Because the envelope is only
honoured when it round-trips byte for byte (see <<_attribution_envelope>>),
an asserted mode is **silently discarded** by any mismatch — so a message
relayed through something that rebuilds, re-wraps or nests the envelope
arrives with no posture at all and no error anywhere. Anything forwarding
these messages should pass the envelope through untouched or strip it
deliberately, never reconstruct it.

The posture itself is the one value here a sender is tempted to get wrong on
purpose. The receiver holds a message whose asserted mode differs from its
own, lets a matching one through, and cannot check either way — so the
posture that clears the gate is always available to anyone willing to state
it. Where the gate exists for a user's decision, stating it is spending that
decision on their behalf.

An interoperating client should derive the posture from the spawning session's
launch configuration and refuse to guess when it cannot tell. A caller that
explicitly supplies a posture is making an unverifiable claim. Leaving the
posture unset is the safe failure: a frame with no `from_mode` is held only by
a `bypass` receiver, never by a prompting one.

Both derivations read *launch* flags, so a mode changed mid-session is
invisible. That error runs toward a hold, not through one.

The injected content is handled as a cross-session prompt: it does not invoke
the receiver's slash-command or attachment-processing paths. The observable
restriction matters to a client; Claude's internal implementation names do not.

==== Attribution envelope

There is no `from_name` on the wire — that much a capture shows. That the
receiver never looks a name up, rather than looking one up and preferring the
envelope, is [.red]#[code]#.
A session instead ships its identity *inside* `message.content`, as an element
the receiving harness parses out and renders as an attributed peer message. A
frame captured from Claude Code 2.1.272:

[source,json]
----
{"msgV":1,"msg_id":"e1b07b89-3534-45c3-b65b-401b5174afef","type":"user",
 "message":{"role":"user","content":"<cross-session-message from=\"uds:/run/user/0/cc-socks/220501.sock\" hop-chain=\"d31520e4d4d04ef3267e9bc4\" from-name=\"claude-send (build)\" from-mode=\"prompting\">\nhello\n</cross-session-message>"},
 "priority":"next","from":"uds:/run/user/0/cc-socks/220501.sock"}
----

Sending bare text instead injects an anonymous prompt: the peer sees no sender
name and no reply address it trusts.

The attributes are rendered in a fixed order, each omitted when empty:

[cols="2,4"]
|===
| Attribute | Constraint

| `from` | Must match `[A-Za-z0-9%:_/.\-]{1,300}`. [.red]#[code]#
| `from-session` | [.red]#[code]# Only if it matches `^[A-Za-z0-9_-]{1,80}$`. Never seen on the wire.
| `hop-chain` | A single 24-hex token is observed; that the field is comma-joined tokens capped at 32 is [.red]#[code]#. A sender appends its own token; a frame whose chain already contains the receiver is dropped as a relay loop, so send it empty unless relaying.
| `from-name` | [.red]#[code]# `"`, `<` and `>` are **removed, not escaped**; `\p{Cf}\p{Cc}\p{Cs}\p{Zl}\p{Zp}` stripped, trimmed, truncated to 64 characters plus `…`. Dropped if it ends up empty.
| `from-mode` | Exactly `bypass` or `prompting`.
|===

A closing tag inside the body is rewritten to `<\`. [.red]#[code]#

IMPORTANT: The receiver re-renders what it parsed and compares it byte for byte
against the input [.red]#[code]#; anything that does not round-trip is treated as plain
text. The *symptom* is reproducible from outside — a malformed envelope silently
loses attribution — but only the code says the mechanism is a byte comparison
rather than a looser parse.
Attribute order, the single spaces, and the newline after the open tag and
before the close tag are therefore all load-bearing — a wrong order or an extra
space silently costs the whole attribution, with no error anywhere.

=== `control`

[source,json]
----
{"type":"control","action":"rename","name":"new-session-name"}
----

Four actions are dispatched. Anything else logs
_"Unhandled control action"_. [.red]#[code]# Only `peer_message_status` and
`peer_idle_notice` were seen on the wire; `rename` and `notify_when_idle` are
read, not observed.

[cols="2,5"]
|===
| `action` | Frame

| `rename`
| `name` (string, required) — renames the receiving session.

| `peer_message_status`
| `status` ∈ `held`, `denied`, `expired`, `delivered`, `refused`, `dropped`;
  `orig_msg_id`; optional `status_detail`, `drop_reason`, `dropped_msg_ids`
  (array, capped). Delivery feedback for an earlier send. Hand-validated, no
  schema. [.red]#[code]# — the accepted field set and the absence of a schema are read.

| `notify_when_idle`
| [.red]#[code]# `{action, from: string, msg_id: string, from_mode?: string}` — subscribe
  to the receiver's next idle moment. Dropped if the reply address is unshaped,
  outside the socket namespace, or resolves to the sender itself.

| `peer_idle_notice`
| [.red]#[code]# `{action, orig_msg_id: string, state: string, finished_at?, detail?,
  from?, from_mode?}` — the answer to the above.

|===

=== Frames the session sends back

A session emits two frame kinds to a peer's inbox.

IMPORTANT: `peer_message_status` is emitted from the **hold-receipt** path
only — `held`, `denied`, and `delivered` once an approval goes through (the
sender's own handler for `delivered` is guarded by `wasHeld`). An ordinary
message from a same-permission-mode peer is accepted and injected with no
status frame at all, so a client that waits for `delivered` on the normal path
waits forever. Verified by observation: a `--wait status` send to a live
2.1.272 session was injected and reported nothing, timing out.

[cols="2,5"]
|===
| Frame | Fields

| `peer_message_status`
| `{action, status, status_detail?, reason, from, orig_msg_id?, drop_reason?,
  dropped_msg_ids?}`. `refused` is sent on the wire as
  `status:"expired", status_detail:"refused"`. `reason` is fixed prose [.red]#[code]#, e.g.
  for `held`: _"Your message is held for the recipient user's approval before it
  reaches their Claude session (permission-mode parity)"_; for `denied`: _"The
  recipient user declined your message; it was not delivered…"_.

| `peer_idle_notice`
| [.red]#[code]# `state` ∈ `idle` (turn finished, nothing queued; debounced and held while parked items exist), `exited` (shutdown — downgraded to `idle` if it exits while genuinely idle), `unavailable` (subscription cannot be served; retried on transient failures). `finished_at` when a turn-end timestamp exists. `detail` **only** when the subscriber's claimed reply address canonicalises to the socket registered for its ``SO_PEERCRED``footnote:peercred[] pid in the session registry.

|===

A send carries the expected pid and start time of the target, so the sender
verifies the *target's* identity as well — a reply is not delivered to a pid
that has been recycled. [.red]#[code]#

== Connection lifecycle

[cols="1,4"]
|===
| Stage | Behaviour

| Connect
| Logged as _"Client connected"_. Peer credentials are read from the socket. [.red]#[code]#

| First line
| Must arrive complete within **30 s**, else the
  connection is closed: _"Closing a connection that sent no complete line
  within N ms"_. Build the payload before connecting.

| Auth
| [.red]#[code]# If the first line is an auth frame it is consumed here and never
  dispatched. Where auth is required, any line before a valid auth frame is
  dropped and the connection destroyed.

| Lines
| Split on `\n`. Each is ``JSON.parse``d; a failure logs _"Failed to parse JSON
  line"_ and skips **that line only**. A line over **1 MiB** (1,048,576 bytes) drops the
  whole connection.

| Validation
| [.red]#[code]# A string `type` is the only structural requirement;
  then `session_id`, if present, must equal the receiver's. `session_id` is
  **optional** — omit it and the check is skipped. (A client can *confirm* the
  optionality by omitting it, but not the rule.)

| Close
| Remaining buffer is parsed (_"Failed to parse final buffer"_ on error),
  then _"Client disconnected"_. [.red]#[code]#
|===

=== Addressing

Reply addresses use a scheme prefix:

[source]
----
^(?:uds|bridge|did):.{1,200}$
----

`uds:` is the local socket path and the only scheme with a transport here.
`bridge:` and `did:` are other address forms, but they are not local socket
targets. Only `uds:` addresses appear on the wire for this transport.

Hop tokens appear as stable 24-hex values across messages from one session.
That observed shape is sufficient for an interoperating client: preserve the chain when
relaying, or leave it empty when not relaying. The derivation, rotation and
chain-size implementation are not part of this client-facing specification.

==== Which reply targets are accepted

A claimed reply address is validated before anything is sent to it; a rejected
one is logged as _"reply address unshaped or outside our socket namespace"_ and
the status frame is simply not sent. [.red]#[code]# The order is:

. On Windows, the target must have the named-pipe shape `(LOCAL\)?cc-msg-<32 hex>`.
. If the target is in the **same directory as the receiver's own socket**, it is
  accepted for ending in `.sock` — no further checks.
. Otherwise a verified peer pid is required, the file name must match
  `^(\d+(-[0-9a-f]{8})?|[0-9a-f]{1,16})\.sock$`, and the directory must be one of
  `/tmp/cc-socks[-<uid>]`, `/private/tmp/cc-socks[-<uid>]`,
  `/run/user/<uid>/cc-socks` or the Termux equivalent. Where that path carries a
  `<uid>`, it must match one the receiver accepts (below). A directory with no
  uid in its name skips that comparison.

A sender advertising the `reply_across_default_dirs` capability gets the third
rule applied directly, rather than only as a fallback. [.red]#[code]#

The accepted uids are computed once when the inbox binds: the session's own uid,
plus the uid the **host** sees it as — its own uid mapped through
`/proc/self/uid_map` — when that differs. The second is absent outside a user
namespace, or when the mapping is missing or ambiguous. So a session whose
inside-root maps to host uid 1000 accepts reply addresses under both
`/run/user/0/cc-socks` and `/run/user/1000/cc-socks`. This is a check on the uid
*written into the path*, not on who owns the directory. [.red]#[code]#

TIP: A client whose inbox lives in the same directory as its peers — the normal
case on Linux, `/run/user/<uid>/cc-socks/` — takes the second rule and never
reaches any of this.

[#_writing_a_client]
== Writing a client

=== The one-liner

Claude Code prints this recipe in its own log when the inbox binds [.red]#[code]#:

[source,bash]
----
{ echo '{"type":"auth","token":"'"$CLAUDE_CODE_MESSAGING_TOKEN"'"}'
  echo '{"type":"user","message":{"role":"user","content":"hello"}}'
} | socat - UNIX-CONNECT:/run/user/0/cc-socks/<pid>.sock
----

With auth optional (the default), the first line can be omitted entirely:

[source,bash]
----
echo '{"type":"user","message":{"role":"user","content":"status?"}}' \
  | socat - UNIX-CONNECT:/run/user/0/cc-socks/5543.sock
----

NOTE: Send the whole line at once. A connection that dribbles bytes without
completing a line inside 30 s is closed — build the payload first
(`out=$(cmd); printf '%s\n' "$out" | …`).

=== A client that authenticates

IMPORTANT: Send the auth frame unconditionally, even where auth is optional.
It is required by default on Windows, the default follows the platform with no
setting to change it, and a client that omits it there is dropped with no wire
diagnostic at all — just an abrupt close. Where auth is off the frame is
accepted and costs one line.

The sample below still treats the key file as optional, because a third-party
client cannot always read one; prefer the child token
(`CLAUDE_CODE_MESSAGING_TOKEN`) whenever the target is the session that spawned
you.

[source,python]
----
#!/usr/bin/env python3
"""Send a prompt to a running Claude Code session on this machine."""
import hashlib, json, os, socket, sys, glob

def session_socket(pid):
    for d in (f"/run/user/{os.getuid()}/cc-socks", f"/tmp/cc-socks-{os.getuid()}", "/tmp/cc-socks"):
        p = f"{d}/{pid}.sock"
        if os.path.exists(p):
            return p
    raise SystemExit(f"no socket for pid {pid}")

def peer_token(sock_path, pid):
    """Read the peerToken the session published for exactly this socket."""
    name = f"{pid}.{hashlib.sha256(os.path.realpath(sock_path).encode()).hexdigest()}.key"
    path = os.path.expanduser(f"~/.claude/sessions/{name}")
    if not os.path.exists(path):
        return None                      # auth is optional by default
    with open(path) as fh:
        return json.load(fh)["peerToken"]

def send(pid, text):
    sp = session_socket(pid)
    tok = peer_token(sp, pid)
    s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
    s.connect(sp)
    lines = []
    if tok:
        lines.append({"type": "auth", "token": tok})
    lines.append({"type": "user", "message": {"role": "user", "content": text}})
    s.sendall("".join(json.dumps(l) + "\n" for l in lines).encode())
    s.close()

if __name__ == "__main__":
    send(int(sys.argv[1]), sys.argv[2])
----

=== Receiving replies

A `user` message is fire-and-forget: the receiver queues it as a prompt and
answers in its own transcript, not on your connection. To get feedback you must
run an inbox of your own and set `from` to `uds:<your socket>`; the receiver
then sends `control`/`peer_message_status` frames and, if you subscribed with
`notify_when_idle`, a `peer_idle_notice` when it goes idle. Your socket has to
live in one of the standard directories, or the reply target is rejected as
"outside our socket namespace".

=== Finding sessions

`~/.claude/sessions/<pid>.json` holds the session registry (one file per
session, alongside the `.key` files); the socket directory lists live inboxes.
Sockets of dead sessions are swept on startup. [.red]#[code]# (the sweep, not the files —
those you can simply look at).

[#_message_sizes]
== Message sizes

The wire caps a line at 1 MiB (envelope included) and drops the whole
connection over it. That is the transport's limit; it is not the same question
as how much of a message reaches the model, and the two can differ by orders of
magnitude — a transport that carries bytes perfectly into a display that cuts
them looks identical to one that never received them.

Measured from the receiving end, by sending numbered-checkpoint payloads with
sentinels and a nonce and asking the receiving session to report the highest
checkpoint it could see:

[cols="1,1,3"]
|===
| Nominal | On the wire | Result

| 1 KB | 1,087 | intact, 15/15 checkpoints
| 4 KB | 4,097 | intact, 58/58
| 16 KB | 16,419 | intact, 234/234
| 32 KB | 32,799 | intact, 468/468
| 64 KB | 65,559 | intact, 936/936
| 128 KB | 131,081 | intact, 1872/1872
| 256 KB | 262,191 | intact, 3745/3745
| 512 KB | 524,341 | intact, 7490/7490
| ~1 MB | 1,000,019 | intact, 14225/14225 — enveloped to 1,014,898, inside the cap
|===

No cut was found at any size. The largest rung enveloped to 1,014,898 bytes
against the 1 MiB line cap, so the practical ceiling for ordinary text is the
cap itself. Quote-dense content reaches it sooner: escaping can double the
payload, and it is the enveloped line that is measured.

Checkpoints were checked for gaps as well as for the highest number, since a
dropped line in the middle and a cut at the end are different failures and only
one of them lowers the maximum.

IMPORTANT: These are **demonstrated sizes, not a located ceiling**. No cut was
found anywhere, which is not the same as nothing being able to fail. Reasoning
from an absence of failures to a property of the system is how a client ends up
splitting at a boundary nobody established.

=== The limit that actually binds

A receiver stops participating long before the transport does.

One session in this experiment absorbed roughly 1.3 MB across several messages
and then went silent: it still accepted connections, and it answered nothing —
not the next large message, not a 1 KB ping afterwards. Alive at the socket,
gone as a participant, and indistinguishable from a slow reply until it does
not end.

This failure is invisible from the sending side, because every send succeeded.
No delivery receipt can report it either: an acknowledgement says the message
was taken, not that the receiver is still able to think. And unlike a
truncation, the cost is cumulative and shared — a large message that arrives
perfectly still spends a permanent fraction of a budget every later message
draws on.

The evidence does not yet separate two explanations. One receiver died after
1.29 MB across four messages; another survived 1.00 MB in one. That is
consistent with a total-volume ceiling and equally consistent with the fourth
message simply being the one that landed on it — two data points cannot tell
them apart, and this document does not pick the tidier reading.

The experiment that would settle it, recorded so nobody has to re-derive it:
give one fresh receiver 4 × 320 KB and another 1 × 1.28 MB — same total,
different message counts. If only the first stops, the cost is per-message
overhead; if both stop, it is volume; if neither, the timing in the original
run was coincidence.

So "how large may one message be" is the wrong question to size a client by.
The number to budget against is how much a receiver can absorb in total, and a
sender choosing how much of a receiver's context to consume is making a
decision it has no standing to make. Carry small bodies; leave the rest behind
an anchor the receiver can fetch if it judges the content worth the budget.

[#_provenance_and_caveats]
== Provenance and caveats

No documentation of this protocol exists to work from, so it was reconstructed
from two different kinds of evidence — and they do not carry equal weight:

*Observed.* Socket layout, directory and file modes, key-file names (`sha256` of
the socket path, recomputed and matched against every sampled file) and
key-file contents, read off a development host; the frames sessions actually
exchange, captured between two live sessions; and delivery behaviour and message
sizes established by sending to a live session and watching what came back — see
<<_message_sizes>>. These claims survive an upgrade or fail loudly.

*Read.* Only claims still marked [.red]#[code]# below required reading the
Claude Code implementation. They are retained only where an interoperating client needs the
behaviour and a black-box test cannot establish it. Internal names, logging,
unreached constants, and branches that clients do not use are deliberately
not part of the interoperability contract. Everything else in this document
is a claim about a running Claude Code instance: traffic, files, environment,
or externally visible behaviour.

=== Measuring an absence

Several of the behaviours above are only observable as something *not*
happening — a message not held, a status not sent, a notice not arriving. That
makes them easy to measure wrongly, and one trap is worth naming because it
has caught every session that went looking.

The approval notice for a held cross-session message is **asynchronous**. The
send returns first, and the notice follows seconds later. So a test that sends,
sees no notice, and concludes "not held" has measured latency, not behaviour —
the correct reading of no notice yet is *not yet*.

The converse trap is worse, because the notice can appear when nothing was
held. A session emits `peer_message_status` **only on the hold path** — `held`,
then `denied` or `delivered` once the user answers. An ordinary accepted
message is reported on by nobody. A sender therefore treats a bare `delivered`
as the end of a hold it may never have seen the start of, and renders it as
_"approved and released after approval"_.

So an inbox that acknowledges every accepted frame with `delivered` — which is
friendlier than silence, and tempting for exactly that reason — makes every
message sent to it look like one its user had to approve. The symptom is an
approval notice with no approval, no hold and no permission gate anywhere near
it, on a path where the receiver has no approval surface at all. Acknowledging
everything is more talkative than a session, not a faithful imitation of one.
Reserve `delivered` for a real hold that was approved.

Three sessions each published that conclusion within an hour, and each had to
retract it; in two cases the retraction crossed with somebody building further
work on the wrong result. If a test's negative result is an absence, give it a
bounded wait before the absence means anything, and say what the bound was when
reporting it.

The same shape applies to the parity check in <<_user>>: because a matching
mode and an unasserted mode both usually result in delivery, a message getting
through establishes very little about `from_mode`. What discriminates is a
receiver in `bypass`, which holds an unasserted frame and accepts a matching
one.

=== Reverse-engineering residuals for an interoperating client

This is the complete list of facts in this specification that are both needed
by an interoperating client and not establishable by observing Claude Code connections and
their effects alone:

* The receiver's attribution parser requires a byte-for-byte re-render of the
  envelope before it treats the content as attributed. The observable result
  (valid envelopes are attributed and malformed or altered ones become plain
  text) is testable; the implementation mechanism is not.
* The receiver uses the envelope's `from-mode` attribute, rather than the
  frame-level `from_mode`, for the permission-mode gate. This distinction is
  needed to send replies that are not unnecessarily held; it cannot be
  inferred from a successful exchange alone because an unasserted message can
  also be delivered.
* The auth line is consumed before normal dispatch when authentication is
  required. An interoperating client needs this to implement an authenticated inbox, but a
  normal authenticated exchange does not reveal whether the line was consumed
  or merely ignored after validation.

Everything else an interoperating client relies on can be established by black-box probing:
socket and key discovery, newline framing, auth success/failure, peer
credentials, prompt and control frames, attribution rendering, reply-address
behaviour, status/idle messages, attachments, and the effects of permission
mode and malformed input. Details such as exact log strings, internal prompt
flags, Windows-only address branches, cleanup sweeps, and token derivation are
not needed by an interoperating client and are intentionally excluded from the residual list.

Everything a client must produce to send a prompt, and everything it can
receive in reply, is covered above.

WARNING: This is an internal protocol. Anthropic documents the *features*
(cross-session messaging, agents) but not this wire format, and nothing
obliges them to keep it stable — field names, the token scheme and the action
vocabulary can change in any release. Pin the Claude Code version if a client
depends on it, and re-verify after upgrades.

This document exists to make an interoperable local client possible, and
describes only what one process can observe of another's messages on a machine
it controls.
