= Claude Code session-to-session messaging (`uds-messaging`)
:toc:
:toclevels: 3
:description: The undocumented unix-socket protocol Claude Code sessions use to message each other on one machine — socket layout, token authentication, wire format, message types, and how to write a third-party client.
:keywords: claude, claude-code, uds, unix socket, ipc, protocol, reverse engineering, messaging, peer

Claude Code sessions on the same machine talk to each other over unix domain
sockets. The subsystem calls itself `uds-messaging`; it is what backs
cross-session messaging, the idle notifications and the artifact-reply handover.

This page documents the protocol as it exists in **Claude Code 2.1.272**
(`linux-x64`). None of it is published by Anthropic — see
<<_provenance_and_caveats>> before relying on it.

TIP: The shortest possible client is one line of shell — see
<<_writing_a_client>>. Everything else here is detail you only need when that
line is not enough.

== Overview

[cols="1,4"]
|===
| Aspect | Value

| Transport | unix domain socket (Windows: named pipe), one per session
| Framing | newline-delimited JSON, one object per line
| Authentication | 128-bit token, presented as the first line
| Identity | `SO_PEERCRED` pid + process start time + session id
| Message types | `user`, `control` (seven actions)
| Direction | bidirectional; replies go to the sender's own socket
|===

== Transport and discovery

=== Socket location

Each session binds one socket named after its pid:

[source]
----
/run/user/<uid>/cc-socks/<pid>.sock     # primary (Linux, XDG runtime dir)
/tmp/cc-socks[-<uid>]/<pid>.sock        # fallback
/private/tmp/cc-socks[-<uid>]/…         # macOS
/data/data/com.termux/files/usr/tmp/cc-socks…   # Termux
\\.\pipe\LOCAL\cc-msg-<32-hex>          # Windows named pipe
----

The socket file name must match:

[source]
----
^(\d+(-[0-9a-f]{8})?|[0-9a-f]{1,16})\.sock$
----

so a plain pid, a pid with an 8-hex discriminator, or a 16-hex opaque id.

The directory must be mode `0700` and owned by the caller or root; a socket in a
directory failing that check is refused (`ownerRefused`). A process in a user
namespace **without a uid mapping** refuses to bind at all, because file
ownership cannot then be verified — the error suggests `unshare -Ur` or an
explicit `--messaging-socket-path`.

=== Environment and flags

[cols="2,3"]
|===
| Name | Meaning

| `CLAUDE_CODE_MESSAGING_SOCKET`
| Path of *this* session's socket. Exported into the session's own environment
  once the inbox is bound, and inherited by anything it spawns.

| `CLAUDE_CODE_MESSAGING_TOKEN`
| The **child token** (see <<_authentication>>). Exported to child processes so
  hooks and spawned tools can talk back without reading any file.

| `--messaging-socket-path`
| Bind an explicit path instead of the automatic one. When given explicitly, a
  failure to publish the auth key is fatal rather than degraded.
|===

== Authentication

Each session generates **two independent 128-bit tokens** at startup:

[source,javascript]
----
{ peerToken:  randomBytes(16).toString("hex"),   // 32 hex chars, for other sessions
  childToken: randomBytes(16).toString("hex") }  // 32 hex chars, for spawned children
----

They are distributed differently, and that difference is the whole access model:

[cols="1,4"]
|===
| Token | Distribution

| `childToken`
| Placed in `CLAUDE_CODE_MESSAGING_TOKEN` in the environment. Anything the
  session spawns inherits it; nothing else can read it.

| `peerToken`
| Written to a key file under `~/.claude/sessions/` (mode `0700` dir, `0600`
  file). Any process that can read that directory — i.e. the same uid — can
  authenticate to any session of that user.
|===

=== The key file

[source]
----
~/.claude/sessions/<pid>.<sha256(canonical socket path)>.key
----

The 64-hex component is `sha256` of the **canonical socket path** (on Windows,
of `\\.\pipe\<name>`), which binds a key file to one specific socket. Writes go
through `<name>.key.tmp.<hex>` and are renamed into place, so a reader never
sees a partial file. Maximum accepted size is 4096 bytes.

Content:

[source,json]
----
{
  "peerToken": "2f6c…",                     // 32 hex chars
  "procStart": "1162506",                   // /proc/<pid>/stat field 22
  "pidDomain": "linux:<machine-id>:pid:[4026532231]"   // namespace-qualified pid space
}
----

`procStart` and `pidDomain` exist so a recycled pid — or an identical pid in a
different namespace — cannot impersonate the session that published the key.

=== The auth line

The first line of a connection may be an auth frame:

[source,json]
----
{"type":"auth","token":"<32 hex chars>"}
----

The guard is deliberately loose about shape and strict about the token:

[source,javascript]
----
QPr(e) = typeof e === "object" && e !== null && "type" in e && e.type === "auth"
ZPr(tok, keys) = eI(tok, keys.peerToken)  ? "peer"
               : eI(tok, keys.childToken) ? "child"
               : undefined
----

Extra fields are tolerated; the token decides the connection's identity —
`peer` or `child` — and both are accepted.

[cols="2,4"]
|===
| Situation | Behaviour

| Valid token
| Connection authenticated; subsequent lines are processed.

| `authRequired` is set and the token is absent or wrong
| Every line is dropped and the connection destroyed:
  _"Dropped … from a connection that did not authenticate; closing it"_.

| `authRequired` is not set (default)
| Unauthenticated lines are **accepted**. This is the state when the key file
  could not be published: _"peers will send unauthenticated (accepted: auth is
  optional on this platform)"_.
|===

IMPORTANT: In the default configuration the token is not a security boundary —
the `0700` directory is. Any process running as the same uid can both read the
key files and connect to the sockets. Treat session sockets as trusted-uid
surface, not as an authenticated channel.

=== Peer credentials

Independently of the token, the server reads the peer's credentials from the
socket (`SO_PEERCRED`) and derives:

* `verifiedPeerPid` — the connecting process's pid
* `verifiedPeerProcStart` — its start time, to defeat pid reuse
* `ownerUids` — the uids permitted for the socket directory

A message whose `session_id` does not match the receiving session is dropped
(_"Dropping … message: session_id mismatch (got X, expected Y)"_), and a message
that appears to originate from the receiver itself is marked `selfSent`.

== Wire format

* One JSON object per line, `\n`-terminated. The trailing buffer is parsed on
  close, so a final line without a newline still arrives.
* A connection that sends **no complete line within 30 s**
  (`firstLineDeadlineMs`) is closed.
* A line exceeding **1 MiB** (`jat=1048576`) is dropped along with the connection.
* Parse failures are logged and skipped, not fatal: _"Failed to parse JSON
  line"_.

== Message types

Only two types are dispatched. Anything else logs
_"Received unhandled message type"_.

=== `user`

Injects a prompt into the receiving session's queue.

[source,json]
----
{"type":"user","message":{"role":"user","content":"hello"}}
----

[cols="2,4"]
|===
| Field | Meaning

| `message.content` | The prompt text. Missing or non-string content is ignored.
| `msg_id` | Sender-assigned id, **must be an RFC-4122 UUID** — gated by `yOe` in two places. On a `user` frame a non-UUID is *silently omitted* from the origin record, so every later `peer_message_status` arrives without `orig_msg_id` and correlation fails; on `notify_when_idle` a non-UUID makes the whole frame invalid and the subscription is dropped. 32 hex is **not** accepted (that pattern is the Windows pipe name).
| `msgV` | Envelope version; a session sends `1`. The receive path never reads it — optional and ignored.
| `priority` | Queue placement: `"now"`, `"next"` or `"later"` — `(x==="now" or "next" or "later") ? x : "next"`, so absent or unknown silently becomes `"next"`; never a drop. A session sends `"next"`. `"now"` also changes *how* the frame is handled, not just where it queues: `type==="user" && priority==="now" && file_attachments===undefined` is dispatched immediately instead of being appended to `processingChain`, the same bypass control frames get (except `notify_when_idle`). So a `"now"` frame can be processed concurrently with one already in flight.
| `uuid` | Optional string; becomes the injected prompt's uuid. Unvalidated, generated when absent — not a correlation handle.
| `from` | Reply address, `uds:<socket path>` (see <<_addressing>>). This is the address the receiver trusts, independent of the one inside the attribution envelope.
| `from_mode` | Sender's permission posture — exactly `"bypass"` or `"prompting"`; the receiver uses it for permission-mode parity (a `bypass` sender's message may be held for approval).
| `file_attachments` | Array of `{file_uuid, file_name, is_image?, sha256?, file_size?}`. Materialised locally before injection; a prefix naming the received files is prepended to the prompt.
|===

The injected turn is marked `isMeta`, `skipSlashCommands` and
`skipAttachments`, so a peer cannot invoke slash commands in the receiver.

==== Attribution envelope

There is no `from_name` on the wire, and the receiver never looks a sender's
name up — it discards asserted identity and reads only the pid from the socket.
A session instead ships its identity *inside* `message.content`, as an element
the receiving harness parses out and renders as an attributed peer message. A
frame captured from Claude Code 2.1.272:

[source,json]
----
{"msgV":1,"msg_id":"e1b07b89-3534-45c3-b65b-401b5174afef","type":"user",
 "message":{"role":"user","content":"<cross-session-message from=\"uds:/run/user/0/cc-socks/220501.sock\" hop-chain=\"d31520e4d4d04ef3267e9bc4\" from-name=\"claude-send (build)\" from-mode=\"prompting\">\nhello\n</cross-session-message>"},
 "priority":"next","from":"uds:/run/user/0/cc-socks/220501.sock"}
----

Sending bare text instead injects an anonymous prompt: the peer sees no sender
name and no reply address it trusts.

The attributes are rendered in a fixed order, each omitted when empty:

[cols="2,4"]
|===
| Attribute | Constraint

| `from` | Must match `[A-Za-z0-9%:_/.\-]{1,300}`.
| `from-session` | Only if it matches `^[A-Za-z0-9_-]{1,80}$`.
| `hop-chain` | Comma-joined 24-hex tokens, at most 32. A sender appends its own token; a frame whose chain already contains the receiver is dropped as a relay loop, so send it empty unless relaying.
| `from-name` | `"`, `<` and `>` are **removed, not escaped**; `\p{Cf}\p{Cc}\p{Cs}\p{Zl}\p{Zp}` stripped, trimmed, truncated to 64 characters plus `…`. Dropped if it ends up empty.
| `from-mode` | Exactly `bypass` or `prompting`.
|===

A closing tag inside the body is rewritten to `<\`.

IMPORTANT: The receiver re-renders what it parsed and compares it byte for byte
against the input; anything that does not round-trip is treated as plain text.
Attribute order, the single spaces, and the newline after the open tag and
before the close tag are therefore all load-bearing — a wrong order or an extra
space silently costs the whole attribution, with no error anywhere.

=== `control`

[source,json]
----
{"type":"control","action":"rename","name":"new-session-name"}
----

Seven actions are dispatched. Anything else logs
_"Unhandled control action"_.

[cols="2,5"]
|===
| `action` | Frame

| `rename`
| `name` (string, required) — renames the receiving session.

| `peer_message_status`
| `status` ∈ `held`, `denied`, `expired`, `delivered`, `refused`, `dropped`;
  `orig_msg_id`; optional `status_detail`, `drop_reason`, `dropped_msg_ids`
  (array, capped). Delivery feedback for an earlier send. Hand-validated, no
  schema.

| `notify_when_idle`
| `{action, from: string, msg_id: string, from_mode?: string}` — subscribe to
  the receiver's next idle moment. Dropped if the reply address is unshaped,
  outside the socket namespace, or resolves to the sender itself.

| `peer_idle_notice`
| `{action, orig_msg_id: string, state: string, finished_at?, detail?, from?,
  from_mode?}` — the answer to the above.

| `yield_artifact_replies`
| `{action, from: ≤512, msg_id: 1–128, session_id: ≤512, slugs: string[≤128
  each], reason: "resume"\|"claim" (default "claim"), sent_at: finite number,
  claimed_at?: finite number, requester?: {cwd?, tmux?}}`. Requires the
  requester to be a **verified live session of the same conversation**
  (`sessionId` *and* pid must match), else refused.

| `unyield_artifact_replies`
| `{action, orig_msg_id: ≤128, slugs: string[], stopped?: bool}`

| `artifact_replies_yielded`
| `{action, orig_msg_id: ≤128, yielded?, not_held?, refused?}`
|===

NOTE: `list` and `remove` are *not* part of this protocol — they belong to the
Artifacts module, which reuses the identifier `action`.

=== Frames the session sends back

A session emits exactly three frame kinds to a peer's inbox.

IMPORTANT: `peer_message_status` is emitted from the **hold-receipt** path
only — `held`, `denied`, and `delivered` once an approval goes through (the
sender's own handler for `delivered` is guarded by `wasHeld`). An ordinary
message from a same-permission-mode peer is accepted and injected with no
status frame at all, so a client that waits for `delivered` on the normal path
waits forever. Verified by observation: a `--wait status` send to a live
2.1.272 session was injected and reported nothing, timing out.

[cols="2,5"]
|===
| Frame | Fields

| `peer_message_status`
| `{action, status, status_detail?, reason, from, orig_msg_id?, drop_reason?,
  dropped_msg_ids?}`. `refused` is sent on the wire as
  `status:"expired", status_detail:"refused"`. `reason` is fixed prose, e.g.
  for `held`: _"Your message is held for the recipient user's approval before it
  reaches their Claude session (permission-mode parity)"_; for `denied`: _"The
  recipient user declined your message; it was not delivered…"_.

| `peer_idle_notice`
| `state` ∈ `idle` (turn finished, nothing queued; debounced and held while parked items exist), `exited` (shutdown — downgraded to `idle` if it exits while genuinely idle), `unavailable` (subscription cannot be served; retried on transient failures). `finished_at` when a turn-end timestamp exists. `detail` **only** when the subscriber's claimed reply address canonicalises to the socket registered for its `SO_PEERCRED` pid in the session registry.

| `artifact_replies_yielded`
| the answer to a `yield_artifact_replies` request.
|===

Sends carry `expectPeerPid` / `expectPeerProcStart` internally, so the sender
verifies the *target's* identity as well — a reply is not delivered to a pid
that has been recycled.

== Connection lifecycle

[cols="1,4"]
|===
| Stage | Behaviour

| Connect
| Logged as _"Client connected"_. Peer credentials are read from the socket.

| First line
| Must arrive complete within **30 s** (`firstLineDeadlineMs`), else the
  connection is closed: _"Closing a connection that sent no complete line
  within N ms"_. Build the payload before connecting.

| Auth
| If the first line is an auth frame it is consumed here and never dispatched.
  With `authRequired` set, any line before a valid auth frame is dropped and
  the connection destroyed.

| Lines
| Split on `\n`. Each is `JSON.parse`d; a failure logs _"Failed to parse JSON
  line"_ and skips **that line only**. A line over **1 MiB** (`jat=1048576`) drops the
  whole connection.

| Validation
| `typeof frame.type === "string"` is the only structural requirement; then
  `session_id`, if present, must equal the receiver's. `session_id` is
  **optional** — omit it and the check is skipped.

| Close
| Remaining buffer is parsed (_"Failed to parse final buffer"_ on error),
  then _"Client disconnected"_.
|===

=== Addressing

Reply addresses use a scheme prefix:

[source]
----
^(?:uds|bridge|did):.{1,200}$
----

`uds:` is the local socket path and the only scheme with a transport in this
module; `bridge:` is the Remote Control bridge; `did:` is an identity-shaped
address with no local handler — several call paths reject both outright
(`errorCode 9`).

Hop tokens are keyed, not random: `fwe(address) = HMAC-SHA256(key, address)`
truncated to 24 hex, with `key = randomBytes(32)` generated once per process.
A token is therefore stable for a session's lifetime, changes on restart, and
cannot be computed by a third party. The chain keeps the last 32 entries; a
frame whose chain already contains the receiver's own token is dropped as a
relay loop. A reply target is only accepted if it resolves inside
one of the standard socket directories, unless the sender set the
`reply_across_default_dirs` capability.

[#_writing_a_client]
== Writing a client

=== The one-liner

Claude Code prints this recipe in its own log when the inbox binds:

[source,bash]
----
{ echo '{"type":"auth","token":"'"$CLAUDE_CODE_MESSAGING_TOKEN"'"}'
  echo '{"type":"user","message":{"role":"user","content":"hello"}}'
} | socat - UNIX-CONNECT:/run/user/0/cc-socks/<pid>.sock
----

With auth optional (the default), the first line can be omitted entirely:

[source,bash]
----
echo '{"type":"user","message":{"role":"user","content":"status?"}}' \
  | socat - UNIX-CONNECT:/run/user/0/cc-socks/5543.sock
----

NOTE: Send the whole line at once. A connection that dribbles bytes without
completing a line inside 30 s is closed — build the payload first
(`out=$(cmd); printf '%s\n' "$out" | …`).

=== A client that authenticates

[source,python]
----
#!/usr/bin/env python3
"""Send a prompt to a running Claude Code session on this machine."""
import hashlib, json, os, socket, sys, glob

def session_socket(pid):
    for d in (f"/run/user/{os.getuid()}/cc-socks", f"/tmp/cc-socks-{os.getuid()}", "/tmp/cc-socks"):
        p = f"{d}/{pid}.sock"
        if os.path.exists(p):
            return p
    raise SystemExit(f"no socket for pid {pid}")

def peer_token(sock_path, pid):
    """Read the peerToken the session published for exactly this socket."""
    name = f"{pid}.{hashlib.sha256(os.path.realpath(sock_path).encode()).hexdigest()}.key"
    path = os.path.expanduser(f"~/.claude/sessions/{name}")
    if not os.path.exists(path):
        return None                      # auth is optional by default
    with open(path) as fh:
        return json.load(fh)["peerToken"]

def send(pid, text):
    sp = session_socket(pid)
    tok = peer_token(sp, pid)
    s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
    s.connect(sp)
    lines = []
    if tok:
        lines.append({"type": "auth", "token": tok})
    lines.append({"type": "user", "message": {"role": "user", "content": text}})
    s.sendall("".join(json.dumps(l) + "\n" for l in lines).encode())
    s.close()

if __name__ == "__main__":
    send(int(sys.argv[1]), sys.argv[2])
----

=== Receiving replies

A `user` message is fire-and-forget: the receiver queues it as a prompt and
answers in its own transcript, not on your connection. To get feedback you must
run an inbox of your own and set `from` to `uds:<your socket>`; the receiver
then sends `control`/`peer_message_status` frames and, if you subscribed with
`notify_when_idle`, a `peer_idle_notice` when it goes idle. Your socket has to
live in one of the standard directories, or the reply target is rejected as
"outside our socket namespace".

=== Finding sessions

`~/.claude/sessions/<pid>.json` holds the session registry (one file per
session, alongside the `.key` files); the socket directory lists live inboxes.
Sockets of dead sessions are swept on startup.

[#_provenance_and_caveats]
== Provenance and caveats

Derived by unpacking the shipped binary, not from any documentation:

* `/root/.local/share/claude/versions/2.1.272` is a **Bun single-file
  executable**; its JavaScript is embedded as plain text (not bytecode).
* The bundle occupies bytes `187,105,280`–`221,773,824` (33.1 MiB); the
  `uds-messaging` module is a ~69 KB slice of it.
* Every claim above was cross-checked against live state on the build host:
  socket layout, directory modes, key-file names (`sha256` of the socket path
  matched on every sampled file) and key-file contents.

=== Known gaps

Wire-level items not established, all of which a client can work around:

* the full `drop_reason` vocabulary: it is a validated free string, and only
  `queue-full` is confirmed as a compared literal. The status prose names the
  causes — _"rate limit, duplicate, relay loop, or full queue"_
* whether the auth guard enforces the 32-hex token shape on input (it does not
  check it structurally; the comparison against the stored token is what fails)

Everything a client must produce to send a prompt, and everything it can
receive in reply, is covered above.

WARNING: This is an internal protocol. Anthropic documents the *features*
(cross-session messaging, agents) but not this wire format, and nothing
obliges them to keep it stable — field names, the token scheme and the action
vocabulary can change in any release. Pin the Claude Code version if a client
depends on it, and re-verify after upgrades.

Anthropic's Commercial Terms restrict reverse engineering; EU law (Software
Directive, Art. 6) permits decompilation for interoperability under conditions.
This document exists to make an interoperable local client possible.
